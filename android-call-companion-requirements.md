# MO54 Calls: требования к Android companion-приложению

Статус: `ТЗ для разработки`  
Дата: `2026-06-23`  
Этап: `до полноценного CRM-контура`

Целевое устройство v1: `Redmi Note 8 Pro M1906G7G`, Android 10,
`MIUI Global 12.0.8.0(QGGRUXM)`.

## 1. Назначение

`MO54 Calls` — отдельное Android companion-приложение для фиксации рабочих звонков Игоря до запуска полноценного CRM-контура.

Приложение должно:

- фиксировать входящие и исходящие звонки;
- сохранять номер, направление, время начала, время завершения и длительность;
- исследовать и использовать автоматическую запись аудио, если это технически возможно на телефоне Игоря;
- после звонка собирать итог разговора и следующий шаг;
- передавать звонок, итог, задачу и аудио в backend MO54;
- работать при временном отсутствии сети через локальную очередь.

Первый этап не должен превращаться в CRM. Он готовит надежный поток данных о звонках, который позже будет подключен к CRM.

## 2. Границы первого этапа

Входит:

- Android-приложение `MO54 Calls`.
- Минимальный backend API для приема звонков.
- Привязка устройства к пользователю `worker-igor`.
- Локальная история звонков и очередь синхронизации.
- Исследование автоматической записи аудио на телефоне Игоря.
- Приемка APK на телефоне Игоря.

Не входит:

- полноценный CRM-канбан;
- интеграции с Avito, Telegram, VK, Max и сайтом;
- обучение сотрудников;
- автоматическая аналитика продаж;
- публикация приложения в Google Play;
- поддержка нескольких PM как пользовательский сценарий, кроме готовности модели к расширению.

## 3. Роли

| Роль | Что делает |
|---|---|
| Игорь | Пользуется приложением, принимает и совершает звонки, заполняет итог и следующий шаг |
| Разработчик Android | Делает APK, исследует запись звонков, документирует ограничения устройства |
| Backend-разработчик | Делает API приема звонков и файлов |
| Принимающий | Проверяет APK по чеклисту и фиксирует результат приемки |

## 4. Основные сценарии

### 4.1. Первый запуск

1. Игорь устанавливает APK вручную.
2. Открывает приложение.
3. Указывает адрес backend MO54 или выбирает преднастроенный адрес.
4. Вводит pairing code или device token.
5. Приложение привязывает устройство к `worker-igor`.
6. Приложение показывает экран разрешений.
7. Игорь выдает разрешения, необходимые для звонков, уведомлений, микрофона и фоновой работы.
8. Приложение показывает статус готовности.

### 4.2. Входящий звонок

1. На телефон поступает звонок.
2. Приложение фиксирует номер, направление `incoming` и время начала.
3. Если запись аудио поддержана устройством, приложение запускает запись по правилам из технической спецификации.
4. Если возможно, клиенту проигрывается фраза уведомления о записи.
5. После завершения звонка фиксируются время окончания и длительность.
6. Приложение показывает уведомление или открывает экран итога звонка.
7. Игорь заполняет результат, итог и следующий шаг.
8. Данные отправляются в backend.

### 4.3. Исходящий звонок

1. Игорь звонит клиенту.
2. Приложение фиксирует номер, направление `outgoing` и время начала.
3. Если запись аудио поддержана устройством, приложение запускает запись.
4. Если возможно, клиенту проигрывается фраза уведомления о записи.
5. После завершения звонка приложение открывает форму итога.
6. Игорь фиксирует результат и следующий шаг.
7. Данные синхронизируются с backend.

### 4.4. Нет сети

1. Звонок завершен, но backend недоступен.
2. Приложение сохраняет звонок, форму итога и аудио локально.
3. В истории звонка виден статус `Ожидает отправки`.
4. После восстановления сети приложение отправляет данные автоматически.
5. Если отправка не удалась, приложение показывает причину и кнопку повтора.

### 4.5. Запись аудио невозможна

1. Приложение фиксирует звонок и форму итога.
2. Статус записи становится `unsupported`, `permission_denied` или `failed`.
3. Пользователь видит понятную причину.
4. Разработчик фиксирует результат в исследовательском отчете.
5. Приемка аудио проводится по правилам из `call-recording-research-protocol.md`.
6. Для v1 невозможность устойчиво записать обе стороны входящего и исходящего
   звонка является блокирующим результатом spike.

### 4.6. Классификация звонка

1. Каждый обнаруженный звонок временно сохраняется локально со статусом
   `pending_classification` и не отправляется в backend.
2. После звонка пользователь выбирает рабочий или нерабочий сценарий.
3. Рабочий звонок получает итог и переводится в очередь синхронизации.
4. Для `not_work_related` локальные metadata и аудио удаляются транзакционно;
   такой звонок не остается в истории и не передается в backend.
5. Несклассифицированные звонки хранятся локально без автоматического удаления.

## 5. Обязательные поля звонка

| Поле | Обязательность | Описание |
|---|---:|---|
| `localCallId` | Да | Локальный UUID звонка на устройстве |
| `deviceId` | Да | ID привязанного устройства |
| `workerId` | Да | Для первого этапа `worker-igor` |
| `direction` | Да | `incoming` или `outgoing` |
| `phoneRaw` | Да | Номер как получен с устройства |
| `phoneNormalized` | Нет | Номер в нормализованном виде, если возможно; иначе `null` |
| `startedAt` | Да | ISO timestamp начала |
| `endedAt` | Да | ISO timestamp завершения |
| `durationSec` | Да | Длительность в секундах |
| `recordingStatus` | Да | Статус записи аудио |
| `noticeStatus` | Да | Статус уведомления о записи |
| `outcomeStatus` | Да | Результат звонка |
| `summary` | Да, кроме `no_answer` | Итог разговора |
| `nextActionType` | Да для активных клиентов | Следующее действие |
| `nextActionAt` | Да для активных клиентов | Дата/время следующего действия |

## 6. Результаты звонка

Допустимые значения `outcomeStatus`:

- `new_lead` — новый лид;
- `continue_work` — продолжить работу;
- `proposal_needed` — нужно подготовить КП;
- `measurement_needed` — нужен замер;
- `prepayment_or_contract` — клиент готов к предоплате или договору;
- `no_answer` — не дозвонились;
- `lost` — отказ;
- `not_work_related` — локальное действие удаления, не передается в backend;
- `no_action_required` — обработка не требуется.

Для `continue_work`, `proposal_needed`, `measurement_needed`, `prepayment_or_contract` обязателен следующий шаг.

## 7. Следующие действия

Допустимые значения `nextActionType`:

- `call`;
- `message`;
- `prepare_proposal`;
- `schedule_measurement`;
- `send_contract`;
- `check_payment`;
- `other`.

Для каждого следующего действия обязательны:

- дата и время;
- краткий комментарий;
- связь с исходным звонком.

## 8. Требования к форме итога

Форма должна открываться после завершения звонка или через уведомление.

Минимальные элементы:

- номер клиента;
- направление звонка;
- длительность;
- статус записи;
- статус уведомления о записи;
- результат звонка;
- поле итога;
- поле возражения;
- следующий шаг;
- кнопка `Сохранить и отправить`;
- кнопка `Сохранить локально`;
- статус синхронизации.

Форма не должна позволять закрыть активный рабочий звонок без результата. Если звонок не относится к работе, пользователь выбирает `not_work_related`, после чего локальная запись и аудио удаляются.

## 9. Нефункциональные требования

- Приложение должно запускаться на целевом телефоне Игоря.
- Установка через APK вручную.
- Интерфейс должен быть пригоден для быстрого заполнения сразу после разговора.
- Все локальные данные должны переживать перезапуск приложения и телефона.
- Сетевые ошибки не должны приводить к потере звонка или аудио.
- Синхронизация должна быть идемпотентной.
- Аудиофайлы нельзя удалять локально до успешного подтверждения backend.
- Пользователь должен видеть, какие звонки еще не отправлены.
- Пользователь должен отдельно видеть все звонки, ожидающие классификации.
- Для v1 запись обеих сторон входящего и исходящего звонка обязательна.
- Невозможность проиграть автофразу в линию не блокирует запись, но ее реальный
  результат обязательно сохраняется в `noticeStatus`.

## 10. Ограничения Android

Автоматическая запись SIM-звонков зависит от:

- модели телефона;
- версии Android;
- прошивки производителя;
- региона;
- способа установки приложения;
- доступных разрешений;
- системных ограничений записи аудио во время звонка.

Разработчик обязан до финальной реализации провести исследование по `call-recording-research-protocol.md`.

Ориентиры для разработки:

- Android Telecom framework: https://developer.android.com/develop/connectivity/telecom
- `CallScreeningService`: https://developer.android.com/reference/android/telecom/CallScreeningService
- `MediaRecorder`: https://developer.android.com/reference/android/media/MediaRecorder
- Google Play sensitive APIs policy: https://support.google.com/googleplay/android-developer/answer/16558241
