# ТЗ: Транскрибация и саммаризация входящих звонков для CRM

**Версия:** 1.0
**Заказчик:** Igor (микробизнес, Новосибирск)
**Исполнитель:** AI-агент (Claude Code / Codex / Antigravity) под контролем заказчика
**Назначение документа:** пошаговое техническое задание для реализации модуля. Документ самодостаточен: агенту не нужен дополнительный контекст, кроме доступов из раздела «Параметры проекта».

---

## 1. Цель

Входящий звонок клиента должен автоматически:
1. записываться (две стороны раздельными дорожками);
2. расшифровываться в текст (ASR);
3. саммаризироваться в структурированные поля (LLM);
4. сохраняться строкой в таблицу CRM.

Всё работает на собственной инфраструктуре, данные не покидают сервер (ФЗ-152), стоимость минимальна.

## 3. Архитектура

```
Клиент звонит на городской номер
        │  (PSTN)
        ▼
   Оператор (SIP-транк)
        │  (SIP/RTP, только с IP оператора)
        ▼
┌─────────────────────────────────────┐
│  VPS заказчика                       │
│  ┌────────────────────────────────┐  │
│  │ Docker: Asterisk               │  │
│  │  - входящий маршрут            │  │
│  │  - звонок на софтфон (ext)     │  │
│  │  - запись 2 дорожки (MixMonitor)│ │
│  │  - hangup → enqueue job        │  │
│  └──────────────┬─────────────────┘  │
│                 ▼                     │
│  ┌────────────────────────────────┐  │
│  │ Docker: worker (Python)        │  │
│  │  1. GigaAM v3 → транскрипт     │  │
│  │  2. Claude Haiku → JSON        │  │
│  │  3. INSERT в БД                │  │
│  └──────────────┬─────────────────┘  │
│                 ▼                     │
│         PostgreSQL (CRM)             │
│                                      │
│  (рядом, ИЗОЛИРОВАННО, работает      │
│   существующий «Планировщик задач»)  │
└─────────────────────────────────────┘
        ▲
        │ SIP-регистрация (Wi-Fi/моб. интернет)
   Софтфон на Redmi (внутренний номер)
```

Поток данных по звонку: `Asterisk (запись + метаданные) → job → worker (ASR → LLM → БД)`.

## 4. Окружение и предпосылки

- VPS уже существует и используется под приложение «Планировщик задач». **Телефонию разворачивать в отдельных Docker-контейнерах**, чтобы компрометация Asterisk не затронула основное приложение.
- Нужен статический публичный IP (обычно есть; уточнить у хостера).
- У оператора оформить договор (для РФ часто требуется ИП/ООО — проверить заранее; если ИП нет, это блокер раньше всех технических шагов).
- SIP-транк авторизуется по IP и/или логину; статические IP оператора зафиксировать для firewall.
- NTP включён (точные таймстемпы звонков).

## 5. Модули, задачи и критерии приёмки

### M1. Asterisk в Docker
**Задачи:**
- Поднять Asterisk в отдельном контейнере (официальный/проверенный образ либо сборка из Dockerfile).
- Конфиги (`pjsip.conf`/`sip.conf`, `extensions.conf`, секреты) — в смонтированном томе, под версионным контролем (секреты — через `.env`/secrets, не в git).
- Логи Asterisk — в отдельный том, ротация.
- AMI/ARI (если используются) слушают **только localhost**, не наружу.

**Критерий приёмки:** контейнер стартует, Asterisk отвечает, наружу открыты только нужные порты (см. M8), панель управления/AMI недоступны из интернета.

### M2. SIP-транк, номер, входящий маршрут, софтфон
**Задачи:**
- Настроить транк к оператору, зарегистрировать/привязать городской номер.
- Создать один внутренний номер (extension) для софтфона заказчика.
- Диалплан: входящий звонок с транка → звонит на extension софтфона.
- На Redmi установить Linphone, зарегистрировать как extension, проверить двустороннюю слышимость.
- Если выбраны исходящие — добавить исходящий маршрут через транк.

**Критерий приёмки:** реальный звонок с мобильного на городской номер дозванивается до софтфона, связь чистая в обе стороны.

### M3. Запись двумя дорожками + хук на hangup
**Задачи:**
- В диалплане включить запись разговора через `MixMonitor` с раздельными дорожками входящего и исходящего потока (rx/tx в отдельные файлы), чтобы каждую сторону можно было распознать независимо (это даёт разметку «кто говорил» без ML-диаризации).
- Имена файлов содержат уникальный ID звонка, направление, таймстемп.
- В обработчике завершения (`h`-extension или Stasis/ARI) по hangup сформировать job со следующими полями и поставить его в очередь:
  - `call_id`, `direction` (in/out), `caller_number` (CallerID), `callee_number`, `started_at`, `duration_sec`, пути к файлам обеих дорожек.
- **Очередь (MVP):** запись job-файла (JSON) в общий смонтированный каталог `queue/`, который слушает worker. (Альтернатива: HTTP POST на endpoint worker'а.)

**Критерий приёмки:** после завершения звонка в `queue/` появляется корректный job-JSON и два WAV-файла (по одной дорожке на сторону).

### M4. Worker обработки звонков
**Задачи:**
- Отдельный контейнер (Python). Слушает `queue/`, обрабатывает job-ы по одному, идемпотентно (повторный job с тем же `call_id` не дублирует строку).
- Пайплайн на job: ASR (M5) → LLM (M6) → запись в БД (M7).
- Ретраи с backoff на сетевых ошибках LLM; при неустранимой ошибке — статус `failed` + лог, job не теряется.
- Логирование каждого этапа.

**Критерий приёмки:** один job проходит весь путь до строки в БД; искусственный сбой LLM приводит к ретраю, а не к потере звонка.

### M5. ASR — GigaAM v3
**Задачи:**
- Установить `onnx_asr`, модель `gigaam-v3-e2e-rnnt` (CPU).
- Распознать каждую дорожку отдельно (16 kHz; при необходимости ресемпл из 8 kHz телефонии).
- Собрать единый транскрипт с метками сторон, например:
  ```
  [Клиент]: ...
  [Оператор]: ...
  ```
  (сторону определяет, на какой дорожке речь: rx = клиент, tx = оператор — уточнить маппинг на этапе M3.)

**Критерий приёмки:** на тестовой записи получается читаемый транскрипт с корректным разделением сторон.

### M6. Саммаризация — Claude Haiku → строгий JSON
**Задачи:**
- Транскрипт → запрос к Claude (`claude-haiku-4-5`) через прокси заказчика.
- System-промпт требует вернуть **только JSON** без префиксов/markdown (см. раздел 7).
- Ответ безопасно распарсить (снять возможные ```json-ограждения, `try/except`); при невалидном JSON — один ретрай с ужесточённым промптом, затем `failed`.

**Критерий приёмки:** на тестовом транскрипте возвращается валидный JSON по схеме из раздела 7.

### M7. Запись в таблицу CRM
**Задачи (вариант PostgreSQL [default]):**
- Создать таблицу `calls` (схема в разделе 7).
- `INSERT` строки из метаданных + полей JSON; хранить и сырой JSON (`raw_json`) для отладки.
- Уникальный индекс по `call_id` (идемпотентность).

**Альтернатива (Google Sheets):** добавление строки через Sheets API, маппинг тех же полей по колонкам.

**Критерий приёмки:** после звонка в таблице появляется одна корректная строка со всеми полями.

### M8. Безопасность и изоляция
**Обязательный чек-лист:**
- Firewall (ufw/nftables): SIP-сигнализация (`5060/udp`, при необходимости tcp) и RTP-диапазон (`10000–20000/udp` — синхронизировать с конфигом Asterisk) открыты **только с IP-адресов оператора**. Остальным — deny.
- Никаких «дефолтных» открытых SIP-портов в мир.
- В Asterisk: `allowguest=no`, `alwaysauthreject=yes`, сильные пароли extension/транка, ограничение по IP на регистрацию там, где возможно.
- `fail2ban` с фильтром Asterisk (бан по неудачным SIP-аутентификациям).
- Контейнер Asterisk — в отдельной Docker-сети; БД доступна worker'у, но не торчит наружу; «Планировщик» и телефония не делят сетевой доступ без необходимости.
- Секреты — в `.env`/Docker secrets, не в репозитории.
- Регулярные обновления образов.

**Критерий приёмки:** внешнее сканирование показывает закрытые SIP-порты для всех, кроме IP оператора; попытки SIP-брутфорса банятся; компрометация телефонии не даёт доступа к приложению «Планировщик».

## 6. Нефункциональные требования

- **ФЗ-152:** аудио и транскрипты хранятся только на VPS заказчика в РФ; во внешний сервис уходит лишь текст транскрипта в LLM (учесть в политике; при необходимости — заменить LLM на локальную модель).
- **Ресурсы:** при низком объёме ASR на CPU работает в батче после звонка на той же машине. Если объём вырастет/нужен real-time — рассмотреть GPU или потоковую модель (T-one). Вне текущего объёма работ.
- **Надёжность:** потеря job недопустима; все этапы логируются; статусы звонка: `new → transcribed → summarized → stored | failed`.

## 7. Контракты данных

### Схема таблицы `calls` (PostgreSQL)
```sql
CREATE TABLE calls (
    id            BIGSERIAL PRIMARY KEY,
    call_id       TEXT UNIQUE NOT NULL,
    direction     TEXT NOT NULL,            -- in | out
    caller_number TEXT,
    callee_number TEXT,
    started_at    TIMESTAMPTZ NOT NULL,
    duration_sec  INTEGER,
    recording_in  TEXT,                     -- путь к дорожке клиента
    recording_out TEXT,                     -- путь к дорожке оператора
    transcript    TEXT,
    theme         TEXT,                     -- тема звонка
    client_request TEXT,                    -- запрос клиента
    agreements    TEXT,                     -- договорённости
    amount        NUMERIC,                  -- сумма, если прозвучала
    next_step     TEXT,                     -- следующий шаг
    next_date     DATE,                     -- дата следующего шага
    raw_json      JSONB,                    -- полный ответ LLM
    status        TEXT NOT NULL DEFAULT 'new',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### JSON-схема ответа LLM (строго)
```json
{
  "theme": "string",
  "client_request": "string",
  "agreements": "string",
  "amount": "number | null",
  "next_step": "string | null",
  "next_date": "YYYY-MM-DD | null"
}
```

### System-промпт для саммаризации (черновик)
```
Ты обрабатываешь транскрипт телефонного разговора с клиентом небольшой компании.
Верни ТОЛЬКО JSON-объект, без markdown, без пояснений, без обрамляющего текста.
Поля:
- theme: краткая тема звонка (1 фраза)
- client_request: что хочет клиент
- agreements: о чём договорились
- amount: сумма в рублях, если прозвучала, иначе null
- next_step: следующий шаг со стороны компании, иначе null
- next_date: дата следующего шага в формате YYYY-MM-DD, иначе null
Если данных нет — ставь null. Не выдумывай.
```

## 8. Вне зоны охвата (для текущей версии)

- Исходящие кампании/обзвон, IVR, голосовое меню.
- Real-time транскрипция «на лету».
- Диаризация через ML (заменена раздельными дорожками).
- Веб-интерфейс CRM (звонки только пишутся в таблицу существующей системы).
- GPU-инфраструктура.

## 9. Definition of Done (приёмочный сквозной тест)

1. Звоню с обычного мобильного на городской номер.
2. Телефон (софтфон) звонит, отвечаю, говорю тестовую фразу с «суммой» и «договорённостью», кладу трубку.
3. В течение разумного времени в таблице `calls` появляется строка: верные номер, время, длительность; транскрипт с разделением сторон; заполненные `theme`, `client_request`, `agreements`, `amount`, `next_step`.
4. Внешнее сканирование портов: SIP закрыт для всех, кроме IP оператора.
5. Тест брутфорса SIP → IP банится fail2ban.
6. Приложение «Планировщик» продолжает работать, изолировано от телефонии.
