# Архитектура MO54 Calls CRM

## Границы

Проект развертывается из `/opt/asterisk-crm` в собственной Docker-сети и не
изменяет `/opt/mo54`, `mo54.service` или контейнеры существующего продукта.
Web API слушает только loopback хоста. Снаружи он доступен исключительно через
отдельный nginx virtual host `calls.мягкиеокна54.рф` с HTTPS; virtual host MO54
не используется и не редактируется.

## Боевой поток v1: Novofon + мобильная связь

```text
входящий: клиент → номер Novofon → Redmi по обычной мобильной связи
исходящий: CRM в браузере Redmi → Call API Novofon → Redmi → клиент
события:   HTTP-уведомления Novofon → защищенный webhook → PostgreSQL → worker
```

1. Novofon присылает `CALL_END` и/или `RECORD_CALL` только на защищенный HTTPS
   endpoint. Nginx принимает webhook только от `37.139.38.215`; приложение
   дополнительно сверяет секрет в пути и `integration_key` в JSON.
2. API отвечает `2xx` сразу после неизменяемого сохранения исходного события.
   Это защищает от повторной доставки, сбоев worker и изменения порядка событий.
3. Worker идемпотентно связывает `call_session_id` с `calls.source=novofon`,
   нормализует телефон, находит/создает контакт и сопоставляет сотрудника
   Novofon с пользователем CRM.
4. После `CALL_END` CRM показывает завершение звонка. После `RECORD_CALL` она
   хранит только метаданные и защищенный переход к записи у Novofon. Для
   пропущенного входящего создается задача обратного контакта.
5. Сверка Data API за скользящие 24 часа создает те же идемпотентные события и
   восполняет не доставленные webhook.
6. Исходящий начинается только кнопкой CRM. Call API звонит менеджеру на Redmi,
   а после ответа соединяет с клиентом. Один intent имеет ключ
   идемпотентности, поэтому двойное нажатие не делает два вызова.

Состояния пилота: `звонок завершен → ожидается запись → ожидается транскрипт →
готово`; ошибка внешнего API сохраняется отдельно и доступна для повторной
обработки. Пока речевая аналитика Novofon не включена, «ожидается транскрипт»
не запускает ASR, LLM или GigaChat.

## Резервный Asterisk-контур

Asterisk, WireGuard, GigaAM и GigaChat не удаляются: они остаются изолированным
исследовательским/диагностическим контуром. Нестабильность Android keepalive
означает, что этот путь не входит в критерии готовности мобильного v1 и не
должен блокировать прием или исходящие через Novofon.

## Ответственность компонентов

- `novofon`: маршрутизация мобильного вызова, provider recording, Call API,
  Data API и HTTP-уведомления.
- `nginx`: отдельный HTTPS perimeter CRM, IP allowlist webhook и rate limit
  входа; не меняет virtual host MO54.
- `api`: cookie-сессия, CRM-команды, прием webhook и запуск callback через
  Call API; не отдает provider link в обычном JSON-ответе.
- `worker`: асинхронно материализует provider events и выполняет Data API
  reconciliation; не обслуживает пользовательский трафик.
- `asterisk`: сохраненный резервный SIP/запись-контур; не критическая часть v1.
- `postgres`: источник истины, идемпотентность и job lease.
- `api/static`: рабочее место менеджера без отдельного build pipeline.

## Модель данных

Основные сущности: `crm_users`, `contacts`, `companies`, `calls`, `recordings`,
`transcripts`, `transcript_segments`, `call_insights`, `deals`, `call_deals`,
`tasks`, `processing_jobs`, `audit_log`, неизменяемые входящие события Novofon,
метаданные provider recording, запросы callback и связь сотрудника Novofon с
пользователем CRM.

Старые поля таблицы `calls` сохранены как совместимая проекция. Новые клиенты
должны использовать API и доменные таблицы.
