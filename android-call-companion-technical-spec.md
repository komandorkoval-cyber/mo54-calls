# MO54 Calls: техническая спецификация Android-приложения

Статус: `техническое ТЗ для Android-разработчика`  
Дата: `2026-06-23`

## 1. Цель

Создать Android APK `MO54 Calls`, который работает как companion-приложение к MO54:

- фиксирует телефонные звонки;
- записывает аудио при технической возможности;
- собирает итог звонка;
- отправляет данные в backend;
- сохраняет данные локально при ошибках сети.

Приложение не является CRM. Оно готовит поток звонков для будущего CRM-контура.

## 2. Рекомендуемый стек

- Kotlin.
- Android Gradle Plugin актуальной стабильной версии, совместимой с Gradle wrapper проекта.
- AndroidX.
- Native UI: Jetpack Compose или XML Views. Выбор остается за Android-разработчиком, но UI должен быть простым и поддерживаемым.
- Локальная база: Room или другой устойчивый storage. Если используется другой storage, разработчик должен описать причину.
- Сеть: OkHttp/Retrofit или эквивалентный HTTP-клиент.
- Фоновые задачи: WorkManager для повторной синхронизации.
- Минимальная версия: Android 10, API 29.
- Package name: `ru.mo54.calls`.

## 4. Архитектура приложения

Слои:

- `call detection` — получение событий звонка;
- `recording` — управление записью аудио и статусом записи;
- `notice` — попытка уведомить клиента о записи;
- `local storage` — хранение звонков, итогов, очереди и аудио;
- `sync` — отправка в backend и повторы;
- `ui` — экраны привязки, разрешений, истории и итога;
- `diagnostics` — тесты устройства для записи и автофразы.

## 5. Разрешения

Разработчик должен определить минимальный набор разрешений под выбранную реализацию. Базовый список для исследования:

- `READ_PHONE_STATE` — состояние телефона;
- `READ_CALL_LOG` — чтение журнала звонков, если нужно для сверки;
- `READ_PHONE_NUMBERS` — если нужно и поддерживается;
- `RECORD_AUDIO` — запись аудио;
- `POST_NOTIFICATIONS` — уведомления Android 13+;
- `FOREGROUND_SERVICE` — если используется foreground service;
- `FOREGROUND_SERVICE_MICROPHONE` — если используется foreground service с микрофоном;
- `INTERNET` — синхронизация;
- `ACCESS_NETWORK_STATE` — проверка сети;
- `RECEIVE_BOOT_COMPLETED` — восстановление планировщика после перезагрузки, если требуется.

Если для реализации используется роль default dialer, `InCallService`, `CallScreeningService` или другой Telecom API, разработчик должен отдельно описать:

- зачем нужна роль;
- как пользователь ее включает;
- какие ограничения появляются;
- можно ли принять приложение без этой роли.

## 6. Детекция звонков

Приложение должно фиксировать:

- входящий звонок;
- исходящий звонок;
- начало звонка;
- завершение звонка;
- номер телефона, если ОС его предоставляет;
- длительность.

Требование к устойчивости:

- если событие начала пропущено, но найден завершенный звонок в журнале, приложение должно создать запись с пометкой `recovered_from_call_log`;
- если номер скрыт или недоступен, поле `phoneRaw` заполняется значением `unknown`, а событие все равно сохраняется.

## 7. Запись аудио

Запись аудио является исследуемым требованием и должна быть проверена на телефоне Игоря.

Статусы `recordingStatus`:

- `not_attempted` — запись не запускалась;
- `recording` — запись идет;
- `recorded` — аудио успешно сохранено;
- `unsupported` — устройство или ОС не позволяют записывать звонок;
- `permission_denied` — нет разрешения;
- `failed` — была попытка записи, но она завершилась ошибкой;
- `manual_attached` — аудио добавлено вручную.

Разработчик обязан:

- не обещать универсальную запись на всех Android-устройствах;
- проверить входящие и исходящие звонки отдельно;
- проверить слышимость обеих сторон;
- приложить тестовые аудиофайлы к исследовательскому отчету;
- зафиксировать используемый источник аудио и API.

## 8. Автофраза о записи

Целевая фраза:

```text
Разговор записывается для контроля качества обслуживания.
```

Статусы `noticeStatus`:

- `not_attempted`;
- `played_to_call`;
- `played_locally_only`;
- `unsupported`;
- `failed`;
- `confirmed_manually`.

Если технически невозможно гарантированно проиграть фразу в линию звонка, приложение должно:

- показать это в диагностике;
- сохранить статус `unsupported`;
- позволить пользователю отметить ручное уведомление;
- передать статус в backend.

## 10. Синхронизация

Правила:

- до классификации звонок не отправляется;
- `not_work_related` транзакционно удаляет metadata и локальный аудиофайл;
- сначала отправляется metadata звонка;
- затем аудио, если есть;
- затем итог и следующий шаг;
- каждая операция должна быть безопасна для повторной отправки;
- при ошибке сеть/backend операция остается в очереди;
- retry должен использовать backoff;
- пользователь должен видеть статус.

Статусы `syncStatus`:

- `local_only`;
- `pending`;
- `syncing`;
- `synced`;
- `failed`;
- `needs_user_action`.

## 12. Безопасность

- Device token нельзя хранить в открытом виде, если выбранный Android storage позволяет безопасное хранение.
- Аудиофайлы хранить в app-specific storage.
- Не писать аудио в публичную папку без явного действия пользователя.
- Для передачи использовать HTTPS.
- В логах приложения не хранить токены и полные payload с персональными данными.

Справка Android по app-specific storage: https://developer.android.com/training/data-storage/app-specific

## 13. Сборка и поставка

Разработчик должен передать:

- список поддержанных Android versions;

- список известных ограничений.

## 14. Критерии технической готовности

- APK устанавливается вручную.
- Приложение привязывается к backend.
- Звонки сохраняются локально.
- Итоги звонков сохраняются локально.
- Синхронизация работает с повторами.
- Backend получает metadata, итог и аудио.
- Диагностика записи оформляет результат по протоколу.
- Потеря сети не приводит к потере данных.
- Входящие и исходящие вызовы стабильно записываются с разборчивым звуком обеих сторон.
